# JARVIS v0.2 — Core Runtime Specification

**Status:** Implementation Specification  
**Depends on:** JARVIS Architecture v0.1  
**Primary milestone:** Read-only intelligent runtime  
**First vertical slice:** Morning Business Briefing  
**Default mode:** Human-governed, evidence-first, read-only

---

# 1. Objective

JARVIS v0.2 harus membuktikan bahwa sistem dapat menjalankan siklus:

```text
REQUEST
↓
UNDERSTAND
↓
BUILD CONTEXT
↓
PLAN
↓
AUTHORIZE
↓
EXECUTE TOOLS
↓
VERIFY
↓
SYNTHESIZE
↓
RETURN EVIDENCE
```

Tanpa:

```text
production mutation
autonomous business action
direct SQL
email sending
payment recording
deployment
```

v0.2 adalah **brainstem pertama JARVIS**.

---

# 2. Success Criteria

v0.2 dianggap berhasil ketika request:

```text
"Jarvis, briefing pagi."
```

dapat menghasilkan output berdasarkan data nyata dari system authoritative.

Contoh:

```text
Morning Briefing
27 September 2026

Finance
- 2 invoice overdue
- outstanding Rp18.500.000

Operations
- 1 production job melewati target completion

Inventory
- 3 SKU berada di bawah reorder threshold

Engineering
- 1 workflow CI gagal pada branch aktif

Prioritas
1. Follow-up invoice INV-1021
2. Review production job PJ-219
3. Investigate inventory reservation CI failure

Evidence:
- MGBOS invoice query
- MGBOS production query
- MGBOS inventory query
- GitHub Actions run
```

JARVIS tidak boleh mengarang metric yang gagal diambil.

# 4. Runtime Modules

## Core

`packages/core`

Bertanggung jawab menjalankan request lifecycle.

Conceptual API:

```ts
runJarvis(request)
```

Output:

```ts
JarvisResponse
```

Core tidak mengakses database atau provider secara langsung.

Core hanya mengenal abstraction.

---

## Contracts

`packages/contracts`

Berisi seluruh contract yang digunakan antar-layer.

Contoh:

```text
JarvisRequest
JarvisResponse

Intent
ExecutionPlan
ExecutionStep

ToolDefinition
ToolCall
ToolResult

PolicyDecision

Evidence

RuntimeError
```

Contracts harus:

```text
strict
versioned
serializable
provider-neutral
```

Zod cocok digunakan sebagai runtime validation.

---

# 5. Request Contract

Initial contract:

```ts
type JarvisRequest = {
  requestId: string
  actorId: string

  channel:
    | "chat"
    | "api"
    | "scheduled"

  environment:
    | "local"
    | "test"
    | "staging"
    | "production"

  message: string

  metadata?: {
    timezone?: string
    organizationId?: string
    conversationId?: string
  }
}
```

Tidak boleh menerima:

```text
raw database credentials
service role credentials
arbitrary SQL
unvalidated tool definition
```

# 7. Runtime State Machine

Canonical request lifecycle:

```text
RECEIVED
↓
CLASSIFYING
↓
CONTEXT_BUILDING
↓
PLANNING
↓
POLICY_CHECK
↓
EXECUTING
↓
VERIFYING
↓
SYNTHESIZING
↓
COMPLETED
```

Failure paths:

```text
REJECTED
FAILED
PARTIAL
```

Setiap state transition harus observable.

Contoh log:

```text
request_id=abc
state=PLANNING
```

kemudian:

```text
request_id=abc
state=EXECUTING
```

```ts
type Intent = {
```

Jika confidence rendah:

Tidak perlu membuat intent classifier ML khusus.

Model language reasoning cukup untuk v0.2.

# 11. Planner Contract

Planner menghasilkan structured plan.

```ts
type ExecutionPlan = {
  goal: string

  steps: ExecutionStep[]

  expectedEvidence: string[]

  riskLevel: RiskLevel
}
```

Step:

```ts
type ExecutionStep = {
  id: string

  capability: string

  dependencies: string[]

  required: boolean
}
```

Contoh:

```json
{
  "goal": "Produce morning business briefing",
  "riskLevel": "R1",
  "steps": [
    {
      "id": "finance",
      "capability": "mgbos.finance.summary.read",
      "dependencies": [],
      "required": true
    },
    {
      "id": "operations",
      "capability": "mgbos.operations.summary.read",
      "dependencies": [],
      "required": true
    },
    {
      "id": "engineering",
      "capability": "github.ci.summary.read",
      "dependencies": [],
      "required": false
    }
  ]
}
```

# 12. Planner Rule

Planner memilih **capability**, bukan provider implementation.

Benar:

```text
github.ci.summary.read
```

Salah:

```text
call REST endpoint /repos/.../actions/runs
```

Detail provider ditentukan Tool Registry.

---

# 13. Policy Engine

Policy Engine harus berjalan **sebelum setiap tool execution**.

Input:

```ts
type PolicyRequest = {
  actorId: string
  environment: string
  capability: string
  riskLevel: string
}
```

Output:

```ts
type PolicyDecision =
  | { decision: "allow" }
  | { decision: "deny"; reason: string }
  | { decision: "require_confirmation"; reason: string }
```

v0.2:

Semua tools adalah:

```text
R0 / R1
READ ONLY
```

Sehingga kebanyakan:

```text
ALLOW
```

Tetapi architecture tetap sudah siap untuk mutation.


# 18. Execution Engine

v0.2 execution engine sederhana.

Algorithm:

```text
for each ready step

Policy Check
↓
Resolve Tool
↓
Validate Input
↓
Execute
↓
Validate Output
↓
Store Evidence
```

Independent read operations boleh parallel.

Contoh:

```text
finance
operations
inventory
engineering
```

bisa dipanggil paralel.

Tetapi optimization ini bukan requirement pertama.

Correctness lebih penting.

# 21. Verification Engine

v0.2 verification fokus pada data quality.

Checks:

```text
tool succeeded
schema valid
timestamp available
data not obviously stale
organization scope correct
required fields present
```

Contoh:

```text
Financial summary generated:
2026-09-27 09:57

Current time:
2026-09-27 10:02
```

valid.

Kalau data terakhir:

```text
2026-09-24
```

response harus mengatakan:

```text
"Financial data terlihat stale."
```

Bukan mempresentasikan sebagai kondisi sekarang.



```text

```

