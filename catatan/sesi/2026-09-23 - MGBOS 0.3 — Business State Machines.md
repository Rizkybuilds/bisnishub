# MGBOS 0.3 — Business State Machines

Sekarang kita menentukan **bagaimana setiap entitas bergerak dari satu kondisi ke kondisi berikutnya**.

Ada satu keputusan arsitektur yang menurut saya sangat penting untuk kita lock terlebih dahulu:

> **Jangan jadikan `order.status` sebagai tempat menumpuk status pembayaran + produksi + QC + pengiriman sekaligus.**

Kalau kita melakukan itu, suatu hari kita akan punya status absurd seperti:

```text
PARTIALLY_PAID_IN_PRODUCTION_WAITING_QC
```

Sebaliknya, setiap domain punya state machine sendiri.

```text
ORDER
Commercial lifecycle

INVOICE / PAYMENT
Financial lifecycle

PRODUCTION JOB
Operational lifecycle

QC
Quality lifecycle

SHIPMENT
Fulfillment lifecycle
```

Lalu Founder Command Center menggabungkan semuanya menjadi kondisi bisnis yang mudah dipahami.

---

# 1. Fundamental State Machine Architecture

Setiap perubahan penting mengikuti pola:

```text
COMMAND
   ↓
CHECK GUARDS
   ↓
AUTHORIZED?
   ↓
DATABASE TRANSACTION
   ↓
STATE TRANSITION
   ↓
BUSINESS EVENT
   ↓
AUTOMATION
   ↓
SIDE EFFECT
```

Contoh:

```text
Confirm Order
      ↓
Does order have customer?
Does it have order items?
Price valid?
Approval completed?
      ↓
YES
      ↓
DRAFT → CONFIRMED
      ↓
order.confirmed
      ↓
Create invoice / task / production preparation
```

Artinya aplikasi tidak boleh melakukan:

```sql
UPDATE orders
SET status = 'CONFIRMED'
```

secara sembarangan.

Harus melalui **business command**.

---

# 2. State Machine hidup di application layer

Untuk v1, jangan membangun configurable workflow engine di database.

State machine didefinisikan di source code.

Contohnya secara konsep:

```text
DRAFT
 ├── confirm → CONFIRMED
 └── cancel  → CANCELLED

CONFIRMED
 ├── activate → ACTIVE
 ├── hold     → ON_HOLD
 └── cancel   → CANCELLED
```

Database hanya menjaga:

```text
current state
timestamps
historical transitions
```

Business service menjaga:

```text
valid transitions
guards
authorization
side effects
```

# 5. Lead State Machine

Lead adalah **inquiry sebelum menjadi sales opportunity yang valid**.

Canonical states:

|State|Makna|
|---|---|
|`NEW`|Lead baru masuk|
|`CONTACTED`|Sudah ada komunikasi|
|`QUALIFYING`|Sedang divalidasi|
|`QUALIFIED`|Layak ditindaklanjuti|
|`DISQUALIFIED`|Tidak memenuhi kriteria|
|`CONVERTED`|Sudah menjadi opportunity|
|`LOST`|Lead valid tapi tidak berlanjut|

Flow utama:

```text
NEW
 ↓
CONTACTED
 ↓
QUALIFYING
 ├────────────→ DISQUALIFIED
 ↓
QUALIFIED
 ↓
CONVERTED
```

Alternative:

```text
NEW
 ↓
LOST
```

# 6. Lead Guards

Contoh transition:

```text
QUALIFYING → QUALIFIED
```

Guard mungkin:

```text
valid contact
+
requirement sufficiently clear
+
commercially relevant
```

Decision Engine yang sebelumnya sudah kita bangun untuk:

```text
Budget
Need
Email
```

sebenarnya merupakan contoh sederhana dari **qualification guard** ini.

Nantinya setiap brand bisa mempunyai rules sendiri.

TeeStock Custom Atelier mungkin:

```text
valid contact
+
custom requirement identifiable
```

sementara MultiGraph B2B mungkin memiliki qualification rules berbeda.

# 8. Requirement State Machine

Requirement membutuhkan lifecycle tersendiri karena quotation bergantung padanya.

States:

```text
DRAFT
↓
NEEDS_INFORMATION
↓
READY
↓
LOCKED
```

Dan terminal:

```text
CANCELLED
```

`LOCKED` berarti requirement version tersebut sudah dipakai untuk commercial artifact penting seperti quote sent/accepted.

Perhatikan:

```text
Requirement
```

bisa terus hidup.

Tetapi:

```text
Requirement Version
```

bersifat immutable setelah dikunci.

# 10. Opportunity State Machine

Opportunity merepresentasikan **deal yang nyata**.

Saya sarankan pipeline:

```text
DISCOVERY
↓
REQUIREMENT_CONFIRMED
↓
PROPOSAL
↓
NEGOTIATION
├────────→ ON_HOLD
↓
WON
```

Terminal lain:

```text
LOST
```

Jadi canonical stages:

|Stage|Makna|
|---|---|
|`DISCOVERY`|Memahami kebutuhan|
|`REQUIREMENT_CONFIRMED`|Scope cukup jelas|
|`PROPOSAL`|Quotation/proposal sedang disusun/dikirim|
|`NEGOTIATION`|Harga/scope sedang dinegosiasikan|
|`ON_HOLD`|Customer menunda|
|`WON`|Deal diterima|
|`LOST`|Tidak jadi|

# 11. Jangan update probability secara AI tanpa konteks

Kita boleh memiliki:

```text
probability_percent
```

tetapi jangan menganggap:

```text
NEGOTIATION = 80%
```

selalu benar.

Awalnya probability bisa manual atau berdasarkan historical conversion setelah data cukup.

AI boleh memberikan estimation sebagai:

```text
ai_recommendation
```

bukan canonical fact.

# 12. Quote State Machine

Quote punya lifecycle yang sangat penting.

```text
DRAFT
 ↓
SENT
 ↓
 ├────────→ REJECTED
 ├────────→ EXPIRED
 ↓
ACCEPTED
```

Ketika ada revisi:

```text
SENT v1
   ↓
SUPERSEDED

DRAFT v2
   ↓
SENT
```

Canonical quote status:

```text
DRAFT
SENT
ACCEPTED
REJECTED
EXPIRED
SUPERSEDED
CANCELLED
```

---

# 13. Quote Version Rules

Selama:

```text
DRAFT
```

boleh diedit.

Setelah:

```text
SENT
```

tidak boleh silently edit.

Perubahan harus:

```text
Quote v1 SENT
      ↓
Create v2
      ↓
v1 SUPERSEDED
      ↓
v2 DRAFT
```

Ini salah satu invariant paling penting MGBOS.

# 16. Order State Machine — keputusan penting

Saya **tidak** ingin order punya state:

```text
IN_PRODUCTION
READY_TO_SHIP
PARTIALLY_PAID
```

karena itu milik domain lain.

Order adalah **commercial commitment**.

Canonical state:

```text
DRAFT
↓
CONFIRMED
↓
ACTIVE
↓
COMPLETED
```

Exception:

```text
ON_HOLD
CANCELLED
```

---

# 17. Order State Meaning

|State|Makna|
|---|---|
|`DRAFT`|Belum menjadi commitment|
|`CONFIRMED`|Customer sudah menyetujui transaksi|
|`ACTIVE`|Sedang dipenuhi|
|`ON_HOLD`|Seluruh order dihentikan sementara|
|`COMPLETED`|Seluruh obligation selesai|
|`CANCELLED`|Dibatalkan|

`CONFIRMED → ACTIVE` bisa terjadi setelah syarat komersial terpenuhi.

Contoh:

```text
Order confirmed
+
required DP paid
=
ACTIVE
```

Untuk order yang tidak butuh DP:

```text
CONFIRMED → ACTIVE
```

bisa langsung.

---

# 18. Order Activation Guards

Rule dapat berbeda berdasarkan payment terms.

Contoh TeeStock Custom Atelier:

```text
50% deposit required
```

Maka:

```text
invoice.balance
↓
payment allocations
↓
deposit threshold >= 50%
↓
order.activate allowed
```

Sementara customer corporate tertentu mungkin:

```text
NET 30
```

maka production boleh dimulai tanpa DP.

Itulah kenapa guard harus berbasis **commercial terms**, bukan hardcoded:

```text
payment == paid
```

untuk seluruh order.

---

# 19. Order Completion Guards

`ACTIVE → COMPLETED` hanya jika misalnya:

```text
all fulfillment obligations completed
+
no blocking production job
+
required shipment delivered/handed over
```

Pembayaran penuh tidak selalu menjadi syarat operational completion.

Kita bisa punya:

```text
Order COMPLETED

Invoice still outstanding
```

untuk B2B NET 30.

Ini penting.

# 23. Payment tidak diubah menjadi REFUNDED

Ini keputusan akuntabilitas yang penting.

Misalnya:


# 24. Production Job State Machine

Di sinilah operational complexity berada.

Canonical v1:

```text
PLANNED
↓
READY
↓
ASSIGNED
↓
ACCEPTED
↓
IN_PRODUCTION
↓
AWAITING_QC
↓
READY_FOR_HANDOFF
↓
COMPLETED
```

Exception:

```text
ON_HOLD
REWORK
CANCELLED
```

---

# 25. Meaning Production States

|State|Arti|
|---|---|
|`PLANNED`|Job dibuat tetapi belum siap|
|`READY`|Spec/material/input siap|
|`ASSIGNED`|Executor sudah dipilih|
|`ACCEPTED`|Vendor/internal executor menerima|
|`IN_PRODUCTION`|Produksi aktif|
|`ON_HOLD`|Terhenti sementara|
|`AWAITING_QC`|Produksi selesai, menunggu inspeksi|
|`REWORK`|Harus diperbaiki|
|`READY_FOR_HANDOFF`|QC lolos dan siap tahap berikut|
|`COMPLETED`|Job obligation selesai|
|`CANCELLED`|Job dibatalkan|

---

# 26. Kenapa ada READY sebelum ASSIGNED?

Karena job boleh dibuat lebih awal.

Misalnya:

```text
Production Job:
Screen Printing

Status:
PLANNED
```

tetapi artwork belum final.

Setelah:

```text
Artwork approved
Garment available
Spec complete
```

baru:

```text
READY
```

Vendor tidak seharusnya menerima pekerjaan yang requirement-nya belum siap.

# 29. Production Delay bukan status utama

Jangan membuat:

```text
DELAYED
```

sebagai state machine utama.

Karena job bisa:

```text
IN_PRODUCTION
+
DELAYED
```

Delay adalah **condition/flag**, bukan state.

Derived:

```text

```

atau:

```text

```

```text

IN_PRODUCTION

```

Ini jauh lebih bersih.

# 30. QC State Machine

```text
PENDING
↓
IN_PROGRESS
↓
COMPLETED
```

```text

```

```text

REWORK_REQUIRED
```

Jangan mencampur:

```text

```

```text
status
=
apakah inspeksi sudah selesai?

=
hasil inspeksinya apa?
```

---

# 31. QC ↔ Production Integration

Jika:

```text
qc.result = PASS
```

maka:

```text
production_job

AWAITING_QC
→
READY_FOR_HANDOFF
```

Jika:

```text
FAIL
```

maka:

```text
AWAITING_QC
→
REWORK
```

Setelah rework:

```text
REWORK
↓
IN_PRODUCTION
↓
AWAITING_QC
```

QC baru dibuat lagi.

Jadi kita tidak overwrite inspection lama.

# 42. Derived State vs Stored State

Ini salah satu keputusan teknis paling penting.

Ada status yang **disimpan**:

```text
order.status = ACTIVE
production_job.status = IN_PRODUCTION
```

Ada status yang **dihitung**:

```text
OVERDUE
AT_RISK
DELAYED
PARTIALLY_PAID
PARTIALLY_FULFILLED
```

Contohnya:

```text
Order TS-00142

order.status
ACTIVE

derived.payment_status
PARTIALLY_PAID

derived.production_status
IN_PROGRESS

derived.fulfillment_status
NOT_FULFILLED

derived.risk_status
AT_RISK
```

Ini jauh lebih fleksibel.

# 48. Automation tidak boleh menciptakan infinite loop

Contoh buruk:

```text

↓

↓
order.updated
↓
n8n update order
↓
...
```

Karena itu automation harus menggunakan:

```text
specific business events
+
idempotency keys
+
correlation IDs
```

Contoh:

```text

```

Automation menciptakan:

```text
order.activated
```

dengan correlation chain yang sama.

# 51. Risk Levels

Saya sarankan setiap command/action bisa diklasifikasikan:

|Risk|Contoh|Authority|
|---|---|---|
|`LOW`|Create task, draft reply|Automation / AI boleh|
|`MEDIUM`|Vendor recommendation, schedule change|Rule/approval tergantung konteks|
|`HIGH`|Discount besar, cancel order, refund|Human approval|
|`CRITICAL`|Transfer uang, legal commitment besar|Strong human authorization|

Ini akan sangat berguna ketika kita mulai membangun agentic business.

# MGBOS 0.4 — System Architecture berikutnya

Di 0.4 kita akan menentukan **bagaimana seluruh blueprint tadi benar-benar dibangun secara teknis**.

Kita akan menentukan bentuk seperti:

```text
TeeStock Website
MultiGraph Website
Internal MGBOS App
        │
        ▼
   Application/API
        │
        ▼
PostgreSQL / Supabase
        │
        ├──── Event System
        │
        ├──── n8n
        │
        ├──── AI Gateway
        │
        ├──── File Storage
        │
        └──── External Integrations
```

Dan di sana kita perlu mengambil keputusan serius tentang **monolith vs microservices, Supabase/PostgreSQL, authentication, API architecture, event/outbox pattern, n8n boundary, AI Gateway, storage, RBAC/RLS, observability, deployment, environments, backup, secrets, dan bagaimana TeeStock website terhubung ke MGBOS tanpa membuat dua sumber kebenaran**.

Menurut saya **0.3 sekarang sudah cukup solid untuk kita jadikan baseline**. Tahap 0.4 akan menjadi titik di mana semua konsep bisnis yang sudah kita rancang mulai berubah menjadi blueprint software yang benar-benar bisa dibangun secara bertahap.
