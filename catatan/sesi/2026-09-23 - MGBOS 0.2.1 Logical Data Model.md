# MGBOS 0.2.1 — Logical Data Model

Sekarang kita ubah conceptual model sebelumnya menjadi **relational model yang cukup presisi untuk nanti diterjemahkan ke PostgreSQL/Supabase**, tetapi belum menulis migration.

Target desainnya:

```text
Business reality
      ↓
Canonical entities
      ↓
Relational integrity
      ↓
Business rules
      ↓
Events / Automation
      ↓
AI Intelligence
```

Prinsipnya: **database harus menjaga sebanyak mungkin kebenaran struktural sendiri**, bukan berharap semua aplikasi selalu menulis data dengan benar.

---

# 1. Konvensi database MGBOS

Sebelum tabel, kita lock beberapa standar.

|Tipe data|Standar|
|---|---|
|Primary key|`uuid`|
|Foreign key|`uuid`|
|Timestamp|`timestamptz`|
|Currency code|`char(3)` / ISO-4217|
|Uang|`bigint`|
|Quantity|`numeric(18,4)`|
|Percentage|`integer` basis points bila finansial|
|Status|`text + CHECK constraint`|
|Flexible specifications|`jsonb`|
|Historical snapshots|scalar columns + `jsonb` bila kompleks|
|Soft deletion|`archived_at timestamptz`|
|Metadata|`jsonb`, non-authoritative|

Untuk IDR:

```text
amount = 150000

=
Rp150.000
```

Jangan:

```text
150000.00 float
```

Kita **tidak menggunakan floating point untuk uang**.

---

# 2. Kenapa status tidak memakai PostgreSQL ENUM

Saya lebih memilih:

```sql
status text
CHECK (status IN (...))
```

daripada database enum permanen.

Alasannya MGBOS masih berkembang cepat. Menambah state ke `text + check` jauh lebih mudah daripada menjadikan enum database terlalu kaku.

State machine formalnya kita susun di **MGBOS 0.3**.

# 16. Requirement Version immutable

Begitu v2 dibuat:

```text
v1 tetap ada
```

Bukan:

```text
UPDATE v1 menjadi v2
```

Contoh:

```text
REQ-104

v1
80 pcs
DTF

v2
100 pcs
Screen print

v3
120 pcs
Screen print + packaging
```

Quote selalu menunjuk **version tertentu**.

# 17. JSONB boundary untuk requirement

Canonical fields:

```text
quantity
budget
deadline
summary
```

Domain-specific:

```json
{
  "garment": {
    "type": "oversized_tshirt",
    "material": "cotton_combed_24s",
    "color": "black"
  },
  "printing": {
    "method": "screen_print",
    "front": true,
    "back": true
  }
}
```

Rule-nya:

> Kalau field dipakai untuk filtering, reporting, finance, constraint, atau workflow kritikal → relational column.

> Kalau field sangat domain-specific dan berubah antar produk → JSONB.

# 31. Relationship Quote → Order

Biasanya:

```text
quote_version
1 ───────── 0..1
order
```

Tetapi kita jangan membuat constraint unique terlalu ketat dulu.

Karena kelak mungkin satu quote menghasilkan beberapa orders.

Contoh:

```text
5000 pcs
↓
customer split delivery
↓
Order 1
Order 2
```

Jadi logical design lebih aman:

```text
quote_version
1 ───────── N
orders
```

walaupun TeeStock v1 umumnya 1:1.

Kalau lima ini kita jaga, kualitas MGBOS akan jauh lebih baik daripada sistem yang sekadar “CRUD dashboard”.

# Berikutnya: MGBOS 0.3 — Business State Machines

Ini bagian yang sangat penting, karena sekarang kita sudah tahu **apa yang disimpan**.

Berikutnya kita harus menentukan:

> **bagaimana bisnis bergerak.**

Contohnya jangan hanya punya:

```text
order.status
```

tetapi definisikan transisi valid:

```text
DRAFT
↓
CONFIRMED
↓
AWAITING_PAYMENT
↓
READY_FOR_PRODUCTION
↓
IN_PRODUCTION
↓
QC
↓
READY_TO_SHIP
↓
SHIPPED
↓
COMPLETED
```

dan juga exception:

```text
CANCELLED
ON_HOLD
PARTIALLY_FULFILLED
REFUND
REWORK
```

Kita akan membuat state machine terpisah untuk **Lead, Opportunity, Quote, Order, Payment, Production Job, Purchase Order, QC, Shipment, Complaint, Task dan Approval**, lalu menentukan **event apa yang dipancarkan setiap transisi dan automation apa yang boleh bereaksi terhadapnya**.

Itu yang akan mengubah MGBOS dari **database yang rapi** menjadi **mesin operasional bisnis yang nyata**.
