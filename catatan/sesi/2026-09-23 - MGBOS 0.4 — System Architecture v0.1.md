# MGBOS 0.4 — System Architecture v0.1

Sekarang kita sudah punya:

```text
0.1 Business Architecture
        ↓
0.2 Canonical Data Model
        ↓
0.3 Business State Machines
        ↓
0.4 SYSTEM ARCHITECTURE
```

Di tahap ini pertanyaannya berubah dari:

> “Bisnis kita bekerja bagaimana?”

menjadi:

> **“Software seperti apa yang harus kita bangun agar semua aturan bisnis tadi berjalan dengan aman, sederhana, dan scalable?”**

Dan karena posisi kita masih **solo founder + asset-light + TeeStock sebagai pilot**, arsitektur terbaik bukan arsitektur perusahaan 500 engineer.

Prinsip kita:

> **Start simple. Architect for growth. Add complexity only when reality demands it.**

---

## 1. Keputusan utama: Modular Monolith

Untuk MGBOS v1 saya memilih:

**Modular Monolith + Event Driven Integration.**

Bukan microservices.

```text
                    MGBOS
                      │
       ┌──────────────┼───────────────┐
       │              │               │
     Sales          Orders        Production
       │              │               │
    Customer        Finance         Vendor
       │              │               │
     Catalog       Fulfillment       QC
       │              │               │
       └──────────────┼───────────────┘
                      │
                 ONE BACKEND
                      │
                 PostgreSQL
```

Tetapi secara source code:

```text
sales/
orders/
production/
finance/
vendor/
catalog/
customer/
fulfillment/
automation/
ai/
```

tetap dipisahkan.

Jadi kita memperoleh keuntungan microservice dari sisi **domain boundaries**, tanpa membayar kompleksitas microservice seperti service discovery, distributed transactions, banyak database, deployment berbeda, network debugging, dan observability lintas service.

Kalau suatu hari salah satu modul memang perlu dipisahkan menjadi service, boundary-nya sudah tersedia.

# 5. Domain Layer menjadi jantung sistem

Business rule jangan hidup di halaman React.

Jangan seperti:

```text
Button "Confirm Order"

↓

update DB:
status = CONFIRMED
```

Harus:

```text
UI
↓
ConfirmOrder Command
↓
Order Domain Service
↓
validate state
↓
validate permissions
↓
validate commercial rules
↓
transaction
↓
Order CONFIRMED
↓
business event
```

Contohnya secara konseptual:

```text
confirmOrder(orderId)

1. Load order
2. Check current state = DRAFT
3. Check customer exists
4. Check item exists
5. Check pricing valid
6. Check approvals
7. Transition → CONFIRMED
8. Write state_transition
9. Write business_event
10. Commit transaction
```

Ini sangat penting untuk vibe coding.

Kalau kita memberikan rule seperti ini ke AI coding agent, kemungkinan AI merusak logic bisnis jauh lebih kecil.

# 9. Security bukan hanya Auth

Supabase mendukung PostgreSQL Row Level Security, dan dokumentasi mereka sekarang menekankan bahwa tabel yang diekspos lewat Data API perlu diproteksi dengan **RLS sekaligus grants yang sesuai**; `service_role` melewati RLS dan karena itu harus tetap server-side. ([Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security?utm_source=chatgpt.com "Row Level Security | Supabase Docs"))

Jadi architecture kita:

```text
Browser
↓
Publishable key
↓
RLS
```

sementara:

```text
Server / trusted automation
↓
Privileged credentials
```

Service key **tidak pernah masuk browser**. Supabase juga secara eksplisit memperingatkan bahwa secret/service-role keys tidak aman di frontend karena bypass RLS. ([Supabase](https://supabase.com/docs/guides/database/secure-data?utm_source=chatgpt.com "Securing your data | Supabase Docs"))

# 14. Kenapa tidak sekadar Supabase Database Webhook?

Supabase memang menyediakan Database Webhooks untuk `INSERT`, `UPDATE`, dan `DELETE`; mekanismenya asynchronous menggunakan `pg_net`, jadi network request tidak perlu memblokir perubahan database. ([Supabase](https://supabase.com/docs/guides/database/webhooks?utm_source=chatgpt.com "Database Webhooks | Supabase Docs"))

Tetapi saya **tidak ingin menjadikan perubahan tabel mentah sebagai contract bisnis utama**.

Contoh:

```text
orders UPDATE
```

tidak menjelaskan:

> order confirmed?

> alamat berubah?

> staff menambahkan note?

Karena itu:

```text
table change
```

bukan business event.

Yang kita publish:

```text
order.confirmed
payment.confirmed
production.started
qc.failed
```

Database Webhook boleh kita gunakan sebagai mekanisme teknis untuk membangunkan dispatcher, tetapi **canonical event tetap `business_events/outbox`**.

# 16. Cara n8n berkomunikasi dengan MGBOS

Flow:

```text
MGBOS
↓
business_event
↓
outbox
↓
n8n webhook
```

n8n Webhook node memang didesain untuk menerima HTTP events dan memulai workflow. Dokumentasi n8n juga memisahkan test dan production webhook URLs. ([GitHub](https://github.com/n8n-io/n8n-docs/blob/main/docs/integrations/builtin/core-nodes/n8n-nodes-base.webhook/README.md?utm_source=chatgpt.com "n8n-docs/docs/integrations/builtin/core-nodes/n8n-nodes-base.webhook/README.md at main · n8n-io/n8n-docs · GitHub"))

Contoh:

```text
event:
quote.sent

↓

n8n

↓

wait 2 days

↓

call MGBOS:
GET quote status

↓

still SENT?

YES
↓

create follow-up task
```

Perhatikan:

n8n **menanyakan kondisi terbaru ke MGBOS**.

Jangan percaya payload event lama untuk keputusan kritis.

# 46. Architecture Laws MGBOS

Saya ingin **mengunci 10 hukum arsitektur** ini:

> **1. PostgreSQL adalah business source of truth.**

> **2. Tidak ada aplikasi yang boleh melewati domain rules untuk mengubah critical business state.**

> **3. n8n mengorkestrasi; n8n tidak memiliki business truth.**

> **4. AI memberikan intelligence; AI tidak memiliki authority.**

> **5. Business event dibuat bersama transaction yang menghasilkan event itu.**

> **6. External integrations harus idempotent.**

> **7. Historical commercial data tidak boleh berubah diam-diam.**

> **8. Public frontend tidak memiliki privileged database credentials.**

> **9. Setiap tindakan penting harus traceable.**

> **10. Complexity harus dibuktikan perlu sebelum ditambahkan.**

Kalau suatu keputusan teknis bertentangan dengan hukum ini, kita punya alasan kuat untuk menolaknya.
