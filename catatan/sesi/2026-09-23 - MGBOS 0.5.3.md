# MGBOS 0.5.3

## Engineering Specification & Repository Standard v0.1

## 1. Tujuan Dokumen

Dokumen ini menjadi **konstitusi teknis MultiGraph Business OS**.

Semua developer, coding agent, automation, dan implementasi baru harus mengikuti standar ini kecuali ada Architecture Decision Record yang secara eksplisit mengubahnya.

Tujuan utama:

- menjaga codebase tetap konsisten;
    
- mencegah AI membuat arsitektur baru secara sembarangan;
    
- mempertahankan business rules sebagai pusat sistem;
    
- menjaga database sebagai source of truth;
    
- membuat MGBOS mudah dikembangkan oleh satu founder;
    
- tetap memungkinkan sistem bertumbuh ke MultiGraph, NeoPack, Pack Point, Squeegee Studios, dan unit berikutnya.
    

---

# 2. Engineering Philosophy

MGBOS mengikuti prinsip:

```text
Simple enough to operate today.
Structured enough to scale tomorrow.
```

Urutan prioritas:

```text
Correctness
↓
Business integrity
↓
Maintainability
↓
Security
↓
Observability
↓
Performance
↓
Developer convenience
```

Performance optimization tidak boleh mengorbankan business correctness.


CRUD boleh digunakan untuk master data ringan.

# 18. User-Facing Errors

Error ke user harus:

- jelas;
    
- actionable;
    
- tidak membocorkan internals.
    

Contoh baik:

> Order belum dapat diaktifkan karena DP minimum belum terpenuhi.

Bukan:

Untuk IDR:

```text

```

```text
amount
currency
```

Contoh:

```text
amount = 150000
currency = "IDR"
```

# 25. Migration Standard

Semua perubahan schema harus migration.

Dilarang mengubah production schema manual tanpa migration counterpart.

Migration naming:

```text
YYYYMMDDHHMM_description.sql
```

Contoh:

```text
202609231530_create_customer_accounts.sql
```

---

# 26. Migration Rules

Migration harus:

- deterministic;
    
- repeatable pada environment baru;
    
- tidak bergantung data lokal;
    
- tidak menghancurkan production data diam-diam;
    
- memiliki safe defaults;
    
- memperhatikan locking untuk perubahan besar.
    

---

# 27. Dangerous Migration

Perubahan seperti:

```text
DROP COLUMN
DROP TABLE
CHANGE TYPE
SET NOT NULL
```

pada data existing harus melalui explicit review.

Untuk breaking change gunakan:

```text
expand
↓
migrate
↓
contract
```

Contoh:

Tambah kolom baru dulu.

Migrasikan data.

Baru hapus kolom lama setelah aman.

---

# 28. RLS / Authorization Standard

Tabel yang terekspos ke client harus memiliki policy eksplisit.

Default:

```text
deny
```

baru kemudian berikan permission yang diperlukan.

Browser tidak boleh memiliki privileged service credentials.

---

# 29. Service Role Rule

Privileged database credentials:

```text
SERVER ONLY
```

Tidak boleh:

- disimpan di client;
    
- dimasukkan bundle frontend;
    
- commit Git;
    
- dikirim ke browser.
    

---

# 30. Immutable Records

Entity berikut dianggap append-only/immutable sesuai lifecycle:

```text
sent quote versions

business events

state transitions

audit logs

confirmed payment records

AI execution records
```

Correction harus membuat record baru atau corrective event.

Bukan overwrite historical truth.

---

# 31. Soft Delete

Transactional data tidak hard delete.

Gunakan:

```text
archived_at
cancelled_at
voided_at
status
```

Hard delete hanya untuk data ephemeral/non-business-critical tertentu.

---

# 32. Transaction Rule

Semua command yang menghasilkan beberapa perubahan terkait harus atomic.

Contoh:

```text
AcceptQuote

BEGIN

quote → ACCEPTED

opportunity → WON

create business_event

create state_transition

create outbox

COMMIT
```

Semua berhasil atau semuanya rollback.

---

# 33. Event Naming

Event menggunakan:

```text
noun.past_tense
```

Contoh:

```text
lead.created
lead.qualified

quote.sent
quote.accepted

order.confirmed
order.activated

payment.confirmed

production.started

qc.failed

shipment.delivered
```

Jangan:

```text
sendQuote
activateOrder
```

Itu commands.

---

# 34. Event Envelope

Semua business event mengikuti format konsisten:

```text
event_id
event_type
event_version

organization_id
brand_id

entity_type
entity_id

occurred_at

actor_type
actor_id

correlation_id
causation_id

payload

metadata
```

---

# 35. Event Versioning

Event schema harus versioned.

Contoh:

```text
event_type:
order.confirmed

event_version:
1
```

Jika payload berubah secara breaking:

```text
event_version:
2
```

Consumer lama tidak boleh diam-diam rusak.

---

# 36. Correlation & Causation

Contoh:

```text
payment.confirmed
```

memicu:

```text
order.activated
```

Maka:

```text
correlation_id
```

sama.

Dan:

```text
causation_id
```

pada `order.activated` menunjuk event payment tersebut.

Dengan begitu seluruh chain bisa ditelusuri.

---

# 37. Idempotency

Critical external request harus mendukung idempotency.

Contoh:

```text
RecordPayment
```

dari webhook dengan:

```text
idempotency_key
```

Jika request sama datang dua kali:

hasil bisnis tetap satu.

---

# 38. Outbox Standard

Business event dan outbox entry dibuat dalam transaction yang sama.

Outbox memiliki:

```text
PENDING
PROCESSING
PUBLISHED
FAILED
```

Retry harus:

- bounded;
    
- observable;
    
- idempotent.
    

---

# 39. n8n Rules

n8n boleh:

- listen event;
    
- schedule work;
    
- call external APIs;
    
- send notification;
    
- invoke MGBOS command API;
    
- invoke AI Gateway.
    

n8n tidak boleh:

- menjadi source of truth;
    
- menentukan canonical pricing rule sendiri;
    
- langsung memanipulasi critical state;
    
- menyimpan master customer/order sebagai data utama.
    

---

# 48. Audit vs Application Log

Application log:

> apa yang terjadi di software?

Audit log:

> siapa mengubah business data?

Business event:

> apa yang terjadi di bisnis?

State transition:

> lifecycle bergerak dari mana ke mana?

Jangan mencampur empat konsep ini.

# 58. UI Standard

MGBOS adalah operational software.

Prioritas:

```text
clarity
speed
information density
actionability
```

bukan animation.

Setiap detail page idealnya menjawab:

```text
What is this?

What state is it in?

What happened?

```

# 59. UI State Actions

Hanya action valid yang ditampilkan.

Contoh Production Job:

Jika:

```text
status = PLANNED
```

jangan tampilkan:

```text
COMPLETE
```

jika state machine tidak mengizinkan.

UI mengikuti domain.

UI bukan penentu domain.

---

# 60. Optimistic UI

Untuk critical business transitions:

hindari optimistic success yang membuat user melihat state berhasil sebelum server mengonfirmasi.

Contoh:

```text
Confirm Payment
Assign Vendor
Accept Quote
```

harus menunggu authoritative result.

---

# 61. Forms

Semua form harus memiliki:

- server-side validation;
    
- client-side convenience validation;
    
- clear error state;
    
- duplicate submission protection untuk critical action.
    

---

# 62. Empty States

Empty state harus actionable.

Contoh:

> Belum ada vendor. Tambahkan vendor pertama untuk mulai membuat production assignment.

Bukan hanya layar kosong.

---

# 63. Accessibility Baseline

Internal tool tetap harus memiliki:

- proper labels;
    
- keyboard navigation reasonable;
    
- semantic buttons;
    
- clear focus state;
    
- readable contrast.
    

---

# 64. Performance Philosophy

Jangan optimize tanpa evidence.

Baseline:

- pagination untuk list besar;
    
- indexed filtering pada field penting;
    
- lazy load data berat;
    
- avoid N+1 query.
    

Caching hanya ditambahkan ketika ada bottleneck nyata.

---

# 65. Read Models

Complex dashboard tidak query 15 tabel dari UI.

Buat read model/query layer seperti:

```text
order_health

customer_360

vendor_performance

founder_attention_queue
```

Read model dapat dibangun ulang.

Canonical transaction tables tetap sumber kebenaran.

---

# 66. Module Public API

Setiap domain module hanya mengekspos entry point yang diperlukan.

Contoh:

```text
order/index.ts
```

mengekspor:

```text
CreateOrder
ConfirmOrder
ActivateOrder
GetOrder
```

Jangan expose seluruh internal implementation.

---

# 67. Cross-Module Access Rule

Production tidak boleh membaca private internals Order module secara sembarangan.

Gunakan:

- public domain interface;
    
- query interface;
    
- repository yang disepakati;
    
- business events.
    

---

# 68. Circular Dependency Rule

Circular imports antar domain dianggap architecture smell dan harus dihindari.

Jika Order bergantung Production dan Production bergantung Order, pertimbangkan:

```text
shared domain contract
```

atau:

```text
event interaction
```

bukan circular import.

# 79. Agent Prohibited Actions

Coding agent tidak boleh tanpa explicit task:

- mengubah architecture;
    
- menambah framework;
    
- mengganti database;
    
- membuat microservice;
    
- menambah state baru;
    
- mengubah pricing rule;
    
- mengubah auth model;
    
- menghapus migration;
    
- reset database;
    
- hard delete historical records;
    
- memanggil AI provider langsung dari domain;
    
- menulis business logic di n8n;
    
- mengubah schema unrelated;
    
- melakukan broad refactor.

# 81. Agent Database Rule

Agent harus:

5. menjalankan relevant tests;
    
6. menjelaskan data migration jika breaking.

# 85. AGENTS.md — Core Rules

Root repository harus memiliki file `AGENTS.md`.

Isi minimum:

```text
# MultiGraph Business OS Engineering Rules

MGBOS is a modular monolith.

PostgreSQL is the business source of truth.

Do not create microservices unless an approved ADR explicitly requires it.

Do not bypass domain commands to modify critical state.

Do not update order, quote, payment, production, QC,
or shipment state directly from UI or automation.

Historical transaction records must not be silently mutated.

Sent quote versions are immutable.

Money must use integer representation, never float.

Business events must use the canonical event envelope.

n8n is an orchestration layer, not a source of truth.

AI output is never authoritative business data.

External integrations must be idempotent.

Do not add dependencies without clear need.

Do not perform unrelated refactors.

Read the relevant product specification,
state machine, schema, and existing implementation before coding.

Every critical business rule requires tests.

Every schema change requires a migration.

Never expose privileged secrets to the browser.

When uncertain, preserve existing architecture
and implement the smallest safe change.
```

# 99. Locked Engineering Decisions

MGBOS 0.5.3 mengunci baseline berikut:

1. **TypeScript-first.**
    
2. **Next.js untuk application layer awal.**
    
3. **PostgreSQL/Supabase sebagai system of record.**
    
4. **Modular Monolith, bukan microservices.**
    
5. **Monorepo.**
    
6. **Domain commands untuk critical state changes.**
    
7. **State machines ditentukan di domain layer.**
    
8. **Transactional Outbox untuk reliable business events.**
    
9. **n8n hanya automation/orchestration layer.**
    
10. **AI Gateway untuk seluruh model AI.**
    
11. **AI tidak menjadi authoritative business source.**
    
12. **Historical transaction data immutable sesuai lifecycle.**
    
13. **Money menggunakan integer.**
    
14. **Schema changes selalu migration.**
    
15. **Critical business rules wajib memiliki automated tests.**
    
16. **Small vertical slices menjadi default development workflow.**
    
17. **Architecture change membutuhkan ADR.**
    
18. **Coding agent tunduk pada AGENTS.md dan task specification.**

# 100. Exit Criteria MGBOS 0.5.3

Engineering specification dianggap cukup jika coding agent dapat menerima task seperti:

```text
MGBOS-005
Implement Customer Account
```

dan sudah mengetahui:

- di folder mana code harus berada;
    
- layer apa yang boleh disentuh;
    
- bagaimana database migration dibuat;
    
- bagaimana validation bekerja;
    
- bagaimana error ditulis;
    
- bagaimana domain command dibuat;
    
- kapan event diperlukan;
    
- bagaimana tests dibuat;
    
- apa yang tidak boleh diubah.
    

Jika agent masih harus menebak arsitektur fundamental, dokumen engineering kita belum cukup.

Dengan standard ini, task implementasi pertama sudah dapat dimulai tanpa menyerahkan kendali arsitektur kepada AI.

Dengan ini, **blueprint → product spec → implementation backlog → engineering constitution** sudah nyambung utuh.

Tahap paling logis berikutnya adalah **MGBOS 0.5.4 — Repository Bootstrap Specification**, lalu kita definisikan secara konkret isi awal repo: `package.json`, workspace, folder aktual, environment schema, Supabase local config, migration pertama, CI, testing setup, `AGENTS.md`, serta **MGBOS-001 sampai MGBOS-004** sebagai bootstrap sebelum masuk Customer Account.
